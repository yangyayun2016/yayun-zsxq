二，Skills 五原则

Skills  五原则TRACE（信任，可靠性，适用性，规范性，有效性）
一个好的Skill应该是怎样的？
维度	      中文
T	Trust	   信任
R	Reliability	可靠性
A	Adaptability适用性
C	Convention	规范性
E	Effectiveness有效性

我们在使用一个 Skill 时，从发现到使用到复用，怎么判断这个 Skill 的质量如何？

通过梳理平台上线以来积累的真实使用反馈和质量问题，并参考业界通行的 Agent Skill 构建规范与设计模式，我们沉淀出一套覆盖 Skill 全生命周期的评测框架——TRACE。

用户对一个 Skill 质量的担忧，归类后只有五种：

"不敢用"——担心安全问题 → Trust 信任
"不稳定"——上次好用这次崩了 → Reliability可靠性
"找不到/用错了"——不知道什么时候该用它 → Adaptability适用性
"看不懂"——不知道怎么用、文档混乱 → Convention规范性
"没用"——用了但结果不好 → Effectiveness有效性
五类问题，对应五个评测维度。
T信任 R可靠性 稳定性 A适用性 C规范性 E有效性

为什么叫 TRACE
TRACE 是五个评测维度的首字母：

维度	      中文	        它回答的核心问题
T	Trust	   信任	    用着放心吗？
R	Reliability	可靠性	每次都稳吗？
A	Adaptability适用性	该出手时出得来吗？
C	Convention	规范性	写得清楚、改得动吗？
E	Effectiveness有效性	最终交付的结果好用吗？
五个维度从左到右是一条因果依赖链：没有前一层的保障，后一层的得分就立不住。安全是地基，稳定是承重墙，适配是水电通路，规范是施工图纸，有效是最终交付给住户的居住体验。

一一解释

T — Trust 信任
一个让人不放心的工具，功能再丰富也不会被长期留下。

我们在 Trust 维度关注两件事：

安全性。Skill 有没有潜在的可疑代码注入或敏感信息泄露？Skillhub 中的 Skill 均会通过安全检测，并出具安全检测报告，通过安全实验室的交叉扫描来识别，属于硬标准。

国内适配性。核心功能是否能在国内网络环境下直接跑通？是否完整支持中文交互？有没有对国内主流平台和工具链做适配？一个完全依赖海外 API 且未做代理适配的 Skill，在国内环境下基本等于不可用。

Trust 是整条链的起点。一个 Skill 在这一层拿不到高分，意味着它还不具备被广泛推荐的前提。

R — Reliability 可靠性
用户说"好用"，说的是每一次都好用。

可靠性考察三个层面：

运行稳定性——同一个任务反复执行，是否始终能正常返回结果。好的 Skill 有重试机制、超时处理和错误恢复策略，偶尔的网络波动不会让整个流程断掉。

功能完善性——描述里写了五个功能，实际跑下来是不是五个都能用。参数校验、默认值处理、多格式输入这些细节，决定了功能的"实"和"虚"。

异常处理——用户不会永远按标准格式输入。空值、超长文本、特殊字符丢进来时，Skill 是给出友好提示引导修正，还是直接静默无响应，或者抛出一段用户看不懂的错误信息，差别很大。

A — Adaptability 适用性
功能做得再好，如果 Agent 在该调用它的时候没调用，或者在不该调用的时候误触发了，用户的实际体验就是零。

适用性关注的是 Skill 和使用场景之间的匹配精度：

能力边界定义——Skill 有没有把自己的适用范围说清楚？哪些事情它做得好，哪些超出它的能力范围？这直接影响用户的预期管理：看完说明就能判断"这是不是我要的东西"。

触发方式——调用条件写得是否清晰、是否有示例、是否无歧义。太宽泛导致不相关请求被错误引导到这个 Skill，太狭窄导致真正需要它的时候命中不了。

C — Convention 规范性
一个 Skill 上线之后还会被迭代、被他人接手维护、被社区参考。规范性决定的是它在时间维度上的存活能力。

渐进式披露——信息架构是否分层？用户首次接触时看到的是核心能力摘要，还是一屏 3000 字的全量说明？详细参考资料和高级用法是否按层次组织，让用户按需深入？

结构清晰——目录是否规范、模块划分是否合理、命名是否一致。三个月后另一个开发者打开这个 Skill，能不能在 30 秒内找到他要改的地方？

文档质量——有没有贴合实际的使用案例（不是随便编的），有没有输入输出样例让用户知道大概会得到什么，有没有最佳实践告诉用户"这么用效果最好"。

反模式与 FAQ——有没有把"千万别这么用"的场景列出来？用户高频踩的坑有没有提前说明？

E — Effectiveness 有效性
前面四个维度评估的是过程，有效性评估的是结果：用了之后，问题解决了吗？

输出准确性——结果是否正确，逻辑是否自洽，有没有事实性错误。调用流程是否顺畅，返回格式是否符合预期。

内容完整性——面对组合条件、多步骤流程、复杂嵌套场景，Skill 是否还能正确处理。用户需求的各个方面是否都覆盖到了，有没有遗漏关键信息。

开箱即用度——输出拿到手能不能直接用，还是要花大量精力二次加工。

创造力与增值——用户自己做也能做到 60 分，用了你这个 Skill 是不是能到 80 分甚至 90 分。有没有额外的洞察、建议、信息整合，让人觉得"确实比我自己弄要好"。

关于评测
一个真正好的 Skill，五个维度都应在合格线以上。安全但不好用是浪费，好用但不安全是隐患，稳定但不规范是技术债。

近期，我们会对 Skillhub 中的数万个 Skill 进行 AI 评测扫描，评测结果可在 Skill 详情页中查看。评测结果仅供参考，帮助用户快速建立判断、帮助开发者定位改进方向。

Leave a TRACE — 每个好 Skill 都值得被追踪。

二，Skills 五原则

Skills  五原则TRACE（信任，可靠性，适用性，规范性，有效性）
一个好的Skill应该是怎样的？
维度	      中文
T	Trust	   信任
R	Reliability	可靠性
A	Adaptability适用性
C	Convention	规范性
E	Effectiveness有效性

我们在使用一个 Skill 时，从发现到使用到复用，怎么判断这个 Skill 的质量如何？

通过梳理平台上线以来积累的真实使用反馈和质量问题，并参考业界通行的 Agent Skill 构建规范与设计模式，我们沉淀出一套覆盖 Skill 全生命周期的评测框架——TRACE。

用户对一个 Skill 质量的担忧，归类后只有五种：

"不敢用"——担心安全问题 → Trust 信任
"不稳定"——上次好用这次崩了 → Reliability可靠性
"找不到/用错了"——不知道什么时候该用它 → Adaptability适用性
"看不懂"——不知道怎么用、文档混乱 → Convention规范性
"没用"——用了但结果不好 → Effectiveness有效性
五类问题，对应五个评测维度。
T信任 R可靠性 稳定性 A适用性 C规范性 E有效性

为什么叫 TRACE
TRACE 是五个评测维度的首字母：

维度	      中文	        它回答的核心问题
T	Trust	   信任	    用着放心吗？
R	Reliability	可靠性	每次都稳吗？
A	Adaptability适用性	该出手时出得来吗？
C	Convention	规范性	写得清楚、改得动吗？
E	Effectiveness有效性	最终交付的结果好用吗？
五个维度从左到右是一条因果依赖链：没有前一层的保障，后一层的得分就立不住。安全是地基，稳定是承重墙，适配是水电通路，规范是施工图纸，有效是最终交付给住户的居住体验。

一一解释

T — Trust 信任
一个让人不放心的工具，功能再丰富也不会被长期留下。

我们在 Trust 维度关注两件事：

安全性。Skill 有没有潜在的可疑代码注入或敏感信息泄露？Skillhub 中的 Skill 均会通过安全检测，并出具安全检测报告，通过安全实验室的交叉扫描来识别，属于硬标准。

国内适配性。核心功能是否能在国内网络环境下直接跑通？是否完整支持中文交互？有没有对国内主流平台和工具链做适配？一个完全依赖海外 API 且未做代理适配的 Skill，在国内环境下基本等于不可用。

Trust 是整条链的起点。一个 Skill 在这一层拿不到高分，意味着它还不具备被广泛推荐的前提。

R — Reliability 可靠性
用户说"好用"，说的是每一次都好用。

可靠性考察三个层面：

运行稳定性——同一个任务反复执行，是否始终能正常返回结果。好的 Skill 有重试机制、超时处理和错误恢复策略，偶尔的网络波动不会让整个流程断掉。

功能完善性——描述里写了五个功能，实际跑下来是不是五个都能用。参数校验、默认值处理、多格式输入这些细节，决定了功能的"实"和"虚"。

异常处理——用户不会永远按标准格式输入。空值、超长文本、特殊字符丢进来时，Skill 是给出友好提示引导修正，还是直接静默无响应，或者抛出一段用户看不懂的错误信息，差别很大。

A — Adaptability 适用性
功能做得再好，如果 Agent 在该调用它的时候没调用，或者在不该调用的时候误触发了，用户的实际体验就是零。

适用性关注的是 Skill 和使用场景之间的匹配精度：

能力边界定义——Skill 有没有把自己的适用范围说清楚？哪些事情它做得好，哪些超出它的能力范围？这直接影响用户的预期管理：看完说明就能判断"这是不是我要的东西"。

触发方式——调用条件写得是否清晰、是否有示例、是否无歧义。太宽泛导致不相关请求被错误引导到这个 Skill，太狭窄导致真正需要它的时候命中不了。

C — Convention 规范性
一个 Skill 上线之后还会被迭代、被他人接手维护、被社区参考。规范性决定的是它在时间维度上的存活能力。

渐进式披露——信息架构是否分层？用户首次接触时看到的是核心能力摘要，还是一屏 3000 字的全量说明？详细参考资料和高级用法是否按层次组织，让用户按需深入？

结构清晰——目录是否规范、模块划分是否合理、命名是否一致。三个月后另一个开发者打开这个 Skill，能不能在 30 秒内找到他要改的地方？

文档质量——有没有贴合实际的使用案例（不是随便编的），有没有输入输出样例让用户知道大概会得到什么，有没有最佳实践告诉用户"这么用效果最好"。

反模式与 FAQ——有没有把"千万别这么用"的场景列出来？用户高频踩的坑有没有提前说明？

E — Effectiveness 有效性
前面四个维度评估的是过程，有效性评估的是结果：用了之后，问题解决了吗？

输出准确性——结果是否正确，逻辑是否自洽，有没有事实性错误。调用流程是否顺畅，返回格式是否符合预期。

内容完整性——面对组合条件、多步骤流程、复杂嵌套场景，Skill 是否还能正确处理。用户需求的各个方面是否都覆盖到了，有没有遗漏关键信息。

开箱即用度——输出拿到手能不能直接用，还是要花大量精力二次加工。

创造力与增值——用户自己做也能做到 60 分，用了你这个 Skill 是不是能到 80 分甚至 90 分。有没有额外的洞察、建议、信息整合，让人觉得"确实比我自己弄要好"。

关于评测
一个真正好的 Skill，五个维度都应在合格线以上。安全但不好用是浪费，好用但不安全是隐患，稳定但不规范是技术债。
