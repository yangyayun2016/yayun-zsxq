# SP-API 与 Ads API 数据分析实战手册

## 一、数据域字段定义

### 1.1 SP-API（销售域）

SP-API 提供卖家自身的销售与流量数据。核心报表为 `GET_SALES_AND_TRAFFIC_REPORT`（仅限卖家）。关键字段如下：

| 字段 | 含义 |
|----|----|
| `childAsin` / `parentAsin` | 子ASIN / 父ASIN |
| `sku` | 卖家SKU |
| `marketplaceId` | 站点标识 |
| `orderedProductSales` | 订购商品销售额 |
| `netProductSales` | 净销售额 |
| `averageSellingPrice` | 平均售价 |
| `sessions` | 会话数 |
| `pageViews` | 页面浏览量 |
| `buyBoxPercentage` | 购物车赢得率 |

`sessions`、`pageViews` 和 `buyBoxPercentage` 构成流量结构，用于判断Listing的转化能力与流量健康度。

### 1.2 Ads API（广告域）

Ads API 通过异步报表接口获取广告投放数据，需指定 `adProduct`（如 SPONSORED_PRODUCTS）、`reportTypeId` 和 `columns`。关键字段：

| 字段 | 含义 |
|----|----|
| `advertisedAsin` / `advertisedSku` | 投放的ASIN / SKU |
| `campaignName` / `adGroupName` | 广告活动名 / 广告组名 |
| `impressions` | 展示量 |
| `clicks` | 点击量 |
| `cost` | 广告支出 |
| `sales7d` | 7天归因销售额 |
| `orders7d` | 7天归因订单数 |

需注意：卖家账户使用 `sales7d`（7天归因窗口），供应商/作者账户使用 `sales14d`（14天归因窗口）。Ads API仅覆盖最近60天的数据，而SP-API可回溯720天，因此历史广告数据需提前落库存储。

## 二、表关联与数据拼接

### 2.1 关联键选择

两个数据域需要通过共享键进行拼接。核心关联键为 `childAsin`（SP-API）与 `advertisedAsin`（Ads API）。但需注意以下细节：

* Ads API中，`advertisedAsin` 在某些报表类型下可能为空（如仅按关键词投放时），此时需通过 `advertisedSku` 与SP-API的 `sku` 进行兜底关联。
* `campaignName` 和 `adGroupName` 仅存在于Ads侧，用于广告维度的下钻分析。
* 同一ASIN可能跨多个广告活动/广告组，需先在Ads侧按 `advertisedAsin` 聚合后再与SP-API关联。
  \*

### 2.2 拼接逻辑

**步骤一：Ads侧聚合**

对Ads API数据按 `advertisedAsin` + `日期` 进行聚合：

```
广告支出 = SUM(cost)
广告销售额 = SUM(sales7d)
广告订单量 = SUM(orders7d)
展示量 = SUM(impressions)
点击量 = SUM(clicks)
```

**步骤二：SP-API侧准备**

对SP-API数据按 `childAsin` + `日期` 保持明细，提取 `orderedProductSales`、`sessions`、`pageViews`、`buyBoxPercentage` 等字段。

**步骤三：Join**

以 `childAsin = advertisedAsin` + `日期` 为条件进行 LEFT JOIN（以SP-API为主表），确保所有有销售记录的ASIN都被保留。如果某ASIN当期无广告投放，广告字段填充为0。

## 三、核心指标计算

### 3.1 自然销量

```
自然销量 = 总销量 - 广告销量
```

其中：

* **总销量**来自SP-API的 `orderedProductSales` 或订单数量
* **广告销量**来自Ads API的 `sales7d`（7天归因窗口）
  \*

此指标反映去除广告归因后的真实自然销售能力。需注意归因窗口差异：Ads API采用Last-Click归因，7天点击归因窗口（14天归因仅适用于供应商账户），因此广告销售额是“被广告触达后7天内的购买”，并非严格的“广告直接带来的增量销售”。

### 3.2 TACoS（总广告销售成本）

```
TACoS = 广告支出 / 总销售额
```

TACoS与ACoS的核心区别在于**分母**：ACoS的分母是广告归因销售额，仅衡量广告活动自身的效率；TACoS的分母是总销售额（广告+自然），衡量广告对整体业务的杠杆效应。

**数据来源分工**：

* 分子（广告支出 `cost`）来自 **Ads API** 的报表接口
* 分母（总销售额）来自 **SP-API** 的销售报表（`orderedProductSales`），取全量而非广告归因部分
  \*

行业参考：多数品类的健康TACoS为8%-15%。TACoS持续下降而ACoS保持稳定，说明广告正在有效拉动自然销售。

### 3.3 数据关联的底层逻辑

从展示到点击、从会话到购买，指标贯穿付费与自然两个渠道：

```
展示（Ads: impressions）→ 点击（Ads: clicks）→ 会话（SP: sessions）→ 购买（SP: orders）
                                    ↓                              ↓
                              广告支出（Ads: cost）        总销售额（SP: orderedProductSales）
                                    ↓                              ↓
                              ACoS = cost / sales7d        TACoS = cost / 总销售额
                                    ↘                              ↙
                                       自然销量 = 总销量 - 广告销量
```

## 四、实战注意事项

**归因窗口差异**：Ads API的 `sales7d` 反映的是广告点击后7天内的购买，而SP-API的 `orderedProductSales` 统计的是订单实际发生时的销售额。同一笔订单可能出现在两个数据源中，计算自然销量时需确保时间窗口对齐，避免重复或遗漏。

**Ad API报表的异步特性**：Ads API采用异步报表请求模式——先POST创建请求获取 `reportId`，再轮询状态，成功后下载文件。报表生成有延迟（约1-3小时），当日数据可能为部分数据。建议每日定时拉取T-2日数据以确保完整性。

**数据清洗要点**：需在分析前完成以下标准化处理——统一多站点货币格式、标准化 `marketplaceId` 映射（如将 `ATVPDKIKX0DER` 映射为美国站）、统一日期粒度（Ads API按天，SP-API可按天/周/月），以及处理ASIN编码中的逗号转义问题。

**历史数据管理**：Ads API仅保留60天数据，SP-API可回溯720天。建议部署定时ETL任务，每日自动拉取并归档Ads数据，否则超过60天的广告数据将永久丢失，导致历史TACoS分析断档。推荐架构为：SP-API与Ads API分别提取 → 标准化清洗 → 以ASIN+日期为键关联 → 写入分析层数据库。
